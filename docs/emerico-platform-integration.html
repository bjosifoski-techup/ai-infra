Integration Architecture

How the AI Commerce Platform and the AI Infrastructure project connect into a single product. What is shared, what is separate, and what each team needs from the other.

References: ai-commerce-dev-spec.html  ·  ai-infrastructure-dev-spec.html

Overview

One Product, Two Engineering Teams

The Emerico AI Commerce Platform is a single product split into two separate engineering engagements. To the end user it is one website. Behind it, two separate codebases and two teams - each responsible for a distinct layer.

Commerce Team

AI Commerce Platform

Next.js application on Vercel. User-facing: login, AI chat interface, storefront, cart, checkout, subscriptions, order management, and admin panel. Spec: ai-commerce-dev-spec.html

Infrastructure Team

AI Infrastructure

LiteLLM proxy, Keycloak identity provider, MongoDB memory layer, and Zuplo MCP gateway. Powers the AI and identity layers that the Commerce Platform depends on. Spec: ai-infrastructure-dev-spec.html

Identity

Keycloak - Auth for Both Projects

Keycloak is not just an infrastructure component. It is the identity provider for the entire platform, including the Commerce frontend. The Commerce spec lists "NextAuth.js or custom" for auth - Keycloak via NextAuth's Keycloak provider is the intended implementation.

Why Keycloak replaces a custom JWT system

The Commerce spec requires: user login, MFA (TOTP), refresh token rotation, short-lived access tokens, and five-tier role enforcement. Keycloak handles all of this natively. The Infrastructure spec deploys a Keycloak instance specifically labelled "Commerce Platform customer identity." These are the same thing.

Infrastructure team

What Keycloak provides

  • User login and registration
  • TOTP MFA (required by both specs)
  • JWT access token (short-lived, 5 min default)
  • Refresh token rotation (secure HttpOnly cookie strategy)
  • Tier role claim in JWT (tier: silver)
  • User ID in JWT (sub - scopes all memory reads/writes)
  • JWKS endpoint (validates tokens across all services)
Commerce team

How the Commerce app integrates

  • Use NextAuth.js with the Keycloak provider
  • Configure with emerico-frontend client ID (PKCE, public)
  • Access token stored in HttpOnly cookie or forwarded server-side
  • Pass access token as Bearer header on AI chat requests to LiteLLM
  • Stripe webhook fires on plan change - must call Keycloak Admin API to update user's realm role to match the new tier
  • Rate limit enforcement in LiteLLM happens automatically from the tier claim

Separation

What Each Team Owns Independently

These areas have no cross-team dependency. Each team owns, builds, and deploys them without coordination.

Commerce team only

Commerce Platform

  • Next.js application and Vercel deployment
  • Openfront GraphQL integration (cart, orders, returns)
  • Openship order fulfillment sync
  • Stripe subscription billing and webhooks
  • PhotonPay product checkout
  • Storefront UI and product display (AliExpress, BigBuy, CJDropshipping)
  • Admin panel (user management, subscription management)
  • Email integration and in-app notifications
  • Figma design implementation
  • AliExpress audit compliance
Infrastructure team only

AI Infrastructure

  • LiteLLM proxy deployment and configuration
  • Keycloak realm setup and deployment
  • Memory API (Node.js + TypeScript + Mongoose)
  • MongoDB Atlas cluster and schema design
  • Zuplo MCP servers (all 8 partner integrations)
  • Affiliate tracking ID injection (server-side, in Zuplo)
  • Rate limiting enforcement (in LiteLLM, by tier)
  • JWT validation middleware across all infra services
  • Memory scoping by user ID (from Keycloak sub claim)

Note on Dropshipping

Dropshipping Partners Appear in Both Specs

AliExpress, BigBuy, and CJDropshipping appear in both specs for different purposes. They are not duplicated systems - they serve different roles.

PartnerIn Commerce PlatformIn AI Infrastructure (Zuplo)
AliExpress Live product feed and search displayed in the storefront UI. Registered partner with audit compliance requirements. MCP tool exposed to the AI agent for product lookup and search. AI can search products and return results in chat. Affiliate tracking ID injected server-side.
BigBuy Live product feed in storefront. MCP tool for the AI agent to search BigBuy products.
CJDropshipping Live product feed in storefront. MCP tool for the AI agent to search CJDropshipping products.

API keys are shared between teams

Both teams will use the same partner API credentials. The Commerce team makes direct API calls for storefront display. The Infrastructure team wraps the same APIs as MCP tools in Zuplo. Coordinate with the client on which account/credentials to use so both teams use the same registered partner account (especially important for AliExpress, which has audit compliance requirements).

Open Questions

Must Be Resolved at Kickoff

These are not implementation details - they are architecture decisions that block both teams if left unresolved.

1. Admin tier in Keycloak

The Commerce spec defines 6 tiers: Guest, Registered Free, Silver, Gold, Platinum, and Admin. The Infrastructure spec defines 5 tiers: Guest, Free, Silver, Gold, Platinum - no Admin. Should Admin be a sixth Keycloak realm role? If so, what rate limit does it get in LiteLLM (unlimited or same as Platinum)? Both teams must agree before either finalises tier configuration.

2. Tier name canonical spelling

"Registered Free" (Commerce spec) vs "Free" (Infrastructure spec). The Keycloak role name and the LiteLLM team name must match exactly what the Stripe plan uses internally, because the Stripe webhook handler will read the plan name and assign the Keycloak role. Agree on the canonical name now: "free" or "registered_free" - then both teams use that exact string everywhere.

3. How the AI chat request reaches LiteLLM

The Commerce spec says the Next.js app connects to a "GCP-hosted AI agent backend via AG-UI/SSE." The Infrastructure spec describes LiteLLM as the AI gateway. Does the Commerce frontend talk to LiteLLM directly, or does it talk to the GCP agent which internally calls LiteLLM? This changes how JWT forwarding works. Both teams and the client must agree on the exact call path before Phase 1 is finalised.

4. Stripe tier change - who updates the Keycloak role?

When a user upgrades from Free to Gold on Stripe, their Keycloak realm role must also change (from "free" to "gold"), because the LiteLLM rate limit reads from the JWT tier claim. The Commerce team's Stripe webhook handler must call the Keycloak Admin API to reassign the role. The Infrastructure team must provide the Commerce team with a Keycloak Admin service account or client credentials to make that API call. This is a hand-off between teams.
