Context

What We Are Building

An AI infrastructure layer that turns the Emerico AI Commerce Platform into a conversational shopping & booking assistant. A logged-in customer chats with an AI that can search real partner catalogs, book through affiliate links, and remember the customer across sessions.

The brain - LiteLLM Proxy

The front door to the LLM. Validates Keycloak JWTs, enforces per-tier rate limits, maps RBAC, and routes chat requests to the client's self-hosted model.

The hands - MCP Servers via Zuplo

Eight MCP servers expose partner APIs as callable tools, so the LLM can search products and events and generate affiliate deep links that earn commission.

The memory - MongoDB Atlas

Short-term sliding conversation window plus a long-term user profile (preferences, summaries, purchase history). Every record is scoped to one user.

How It Works

Request Lifecycle - One Chat Turn

Understanding this flow is the key to the whole build. Two constants on every hop: the Keycloak JWT travels with the request, and everything is scoped to that user.

1

Customer sends a message

The Vercel frontend attaches the user's Keycloak JWT and calls the LiteLLM proxy.

2

LiteLLM authorizes the request

Validates the JWT via Keycloak JWKS, reads the tier from the role claim, applies the rate limit, and checks RBAC model access.

3

Memory is loaded

The short-term conversation window and relevant long-term profile are fetched from MongoDB and prepended to the LLM context.

4

The self-hosted LLM reasons

The model produces an answer - or decides to call one or more MCP tools to fetch live data.

5

Tool calls run through Zuplo

The gateway applies rate limiting and auth, calls the partner API, and injects Emerico's affiliate tracking parameters into generated links.

6

Result is rendered & remembered

MCP-UI renders product/event cards in the chat; the turn is written back into short-term and (periodically summarized into) long-term memory.

Ground Rules

Architecture Principles

Lock these in before writing code - every later decision depends on them.

1

Keycloak is the single trust anchor. A fresh, dedicated instance - not the SSO realm. All three components validate the same tokens. Build it first.

2

Independent codebase. This engagement does not touch the Commerce Platform repo. It integrates via configured endpoints only.

3

Stateless gateways, stateful memory. LiteLLM and Zuplo hold no user state - they authorize and route. All state lives in MongoDB, keyed by user ID.

4

Defense in depth on user scoping. The JWT sub claim must filter every memory query - enforced in middleware, never left to individual queries.

5

Config via environment. No keys, endpoints, or secrets in code. Every secret below lives in an env var or a secret manager.

6

Clean specs first. Within the MCP phase, build partners with the cleanest OpenAPI specs first to surface effort variance early.

Operator credentials - not env vars

The Elestio account and the Zuplo account are single dashboard logins (email + password, ideally with 2FA) that a person uses to deploy and manage services. They are not application secrets and do not belong in any .env - keep them in a password manager / shared vault. Deployment here is the manual one-click flow, so no ELESTIO_* env var is needed at all. (If deployment is later automated via CI / Terraform, add a single ELESTIO_API_TOKEN secret for that.)

Handling rules

Get externally items are the procurement risk - request the self-hosted LLM URL/key from Emerico and apply for the partner API keys and affiliate IDs at project kickoff, since several affiliate programs need account approval. Store every Secret (regardless of origin) in Elestio / Zuplo environment secrets or a dedicated secret manager - never in the codebase. Commit a .env.example listing all variables with placeholder values only.

Order

Sequencing

Phase 1 is the hard dependency. Phases 2 and 3 are independent of each other and can be parallelized with enough team capacity.

Phase 1 - first

Keycloak is the dependency for everything; LiteLLM is the user-facing critical path. Nothing tests end-to-end until this works.

Phase 2 - parallel

Memory depends only on Keycloak JWT validation. It can be built alongside Phase 3.

Phase 3 - parallel

MCP servers depend on Keycloak auth and a confirmed tool-calling LLM. Independent of memory.

Verification

Testing Strategy & Definition of Done

Testing strategy

  • Phase 1 - valid token passes, invalid/expired rejected; rate limits trigger at the right tier thresholds.
  • Phase 2 - memory persists across turns; long-term preferences affect later answers; cross-user access attempt fails.
  • Phase 3 - each of the 8 servers tested through Zuplo; LLM selects correct tools; cards render; affiliate links tagged.
  • Integration - the full request lifecycle exercised under each user tier.

Release conditions

  • All three components live and verified end-to-end in production.
  • Rate limiting and auth policies applied and tested across all components.
  • Full source code and configuration delivered to the client repository.
  • Technical documentation for all three components delivered.
  • Knowledge-transfer session completed with the client.
